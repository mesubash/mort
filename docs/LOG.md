With it, stalled means that number has not changed for `--stall` minutes, even while the log grows (a job repeating `loss=0.693`). The log's last 16 KB is split on `\n` and `\r` so tqdm bars count. - Kaggle watcher: `mort track kaggle owner/kernel [--pull DIR]`. On finished, `kaggle kernels output -p DIR -q` once, only into an empty or new folder (refused at track time and checked again before download), and the notification says where the output went or why it did not. mort only calls the CLI and never reads the Kaggle token. - GitHub watcher: `mort track github` (off: `mort forget github`). Every 5 min, one `gh api search/issues` for the user's open issues and pull requests updated since the last reply seen, then comments, review comments and reviews on those only. Replies by the user and by bots (`type: Bot`) are skipped. Starts from the time it is turned on, so old replies are not sent. Uses the user's `gh` login; mort stores no token. - ssh watcher: `mort track ssh <host> <path> [--done RE] [--failed RE]`. Each check runs one read-only `ssh -o BatchMode=yes -o ConnectTimeout=10 host tail -n 5 -- <quoted path>`. The last non-empty line decides: default `^DONE` finished, `^FAIL` died, because real STATUS files hold `DONE` or `FAILED-<step>`; per-step files (`s0 DONE` appended per step) need `--done 's2 DONE'` so an early step does not count as the end. A missing file means not started yet. ssh exit 255 or a 20 s timeout is "unknown", never died, and the next try waits 5 min. Finished or died jobs are not read again. The summary and `mort log` show what the daemon last read, so they never open a connection. Host names must not start with `-` (no ssh option injection). `mort kill` refuses remote jobs. Schema: `pid` may be NULL; new columns for kind, target and the last read; `connect()` adds missing columns from a table of them.

Free disk default 4 GB (`disk_min_gb`). An alert stays on until its value is 10% clear of the limit, so a value at the edge does not alert every minute. Sent-once state for machine and stale-lock alerts moved to an `alerts` table (replacing `~/.mort/lock.warned`). The summary shows a MACHINE line.

## 2026-11-25

- `mort kill` on an adopted job now signals the process and all its descendants (found with `ps -A -o pid,ppid`). Signalling only the process left children running: a `run_*.sh` script started under `nohup` dies on TERM while its Python child keeps going. Its process group is not used because an adopted job may share a group with the user's shell. Found while checking: `caffeinate -dims cmd` becomes `cmd` (same PID) and leaves a helper child, so the PID to track is the one running the command.
- Phase 1 "done when", part 2 met on the real lock: a `mort run --lock` job killed with SIGKILL (whole group, no cleanup possible) was reported as died and its lock freed by the daemon 17 s later. Part 1 (a real training run notifies at its end) waits for the next real run.
- Lock PID is now found counting from the end of the line. Real lock writers put several words in the job name (`kiln-adapt mean-teacher seeds <pid> <date>`), so a fixed position from the left was wrong. mort writes `{start}` as `%Y-%m-%d_%H:%M`, the same as `date +%F_%H:%M` in those scripts.
- Task 8: `mort daemon install|uninstall|status`. The launchd agent `mort.check` (`~/Library/LaunchAgents/mort.check.plist`, written with `plistlib`) runs `python -m mort check` every 60 s and at load, logging to `~/.mort/daemon.log`. It is loaded with `launchctl bootstrap gui/<uid>`; reinstall boots out the old one first. Until mort is packaged the agent runs from this checkout through `PYTHONPATH`.
- Task 7: `mort check` applies the rules to every job and sends each new event once (`last_event`). A stalled job that writes again goes back to running, so a later stall alerts again. Notifications go through `osascript` with the text passed as arguments, never inside the script. Stale lock: if its PID belongs to a mort job that took the lock, mort frees it (the crash case in the phase 1 "done when"); a stale lock from another tool is only reported, once per distinct line (`~/.mort/lock.warned`), since mort does not delete what it did not write.
- Task 5: `mort track pid <pid> [--log PATH] [--done TEXT]`. mort cannot learn the exit code of a process it did not start, so `--done` names a success marker: when the process is gone and the last 8 KB of the log contain the text, the job counts as finished; otherwise died (the PLAN rule). Without `--log` there is no stall check. Start time comes from `ps -o lstart`. New column `done_marker`; `connect()` adds it to an older state.db. A job with an exit file now counts as ended even if its PID is reused. PID reuse for adopted jobs is not handled; macOS PIDs wrap slowly, so this waits for a real case.
- Task 4: `mort` (summary), `mort log` (hands off to `tail`), `mort kill`, `mort forget`. The summary reads state and applies the rules but sends nothing; sending belongs to the watcher (task 7). `mort kill` asks first, then signals the job's process group. The wrapper traps TERM so it outlives the kill and still writes the exit code (143) and frees the lock. A killed job is marked as already reported, so the watcher will not alert about a stop the user asked for. `mort forget` keeps the log file.
- `mort run` (task 3): starts `sh -c WRAPPER` in a new session (no hangup when the terminal closes), wrapped in `caffeinate -dims` when that exists (it passes the exit code through, checked). The wrapper writes `$?` to `~/.mort/logs/<name>.exit` and frees the lock only if the lock still names the wrapper's PID, so it never removes a lock another tool wrote. It waits up to 5 s for mort to write the lock first, so a job that ends at once still frees it. A wrapper killed with SIGKILL cannot free the lock; the stale-lock check covers that case.
- Lock config: `[lock] path` and `format` in `~/.mort/config.toml`, with `{name}`, `{pid}`, `{start}`, `{cwd}`. The PID position is read from the format, so there is no separate field number to get wrong. A held lock refuses the run; a stale one is taken over.
- Job names are limited to letters, digits, `.`, `_`, `-`, because they become file names. Run with `python3 -m mort` until packaging.
- Icon: `docs/mort.svg`, an original ghost peeking over a terminal (mort is French for death). Animated with CSS inside the SVG: slow glance left and right, smile and blush when facing the viewer, blink, bob, finger taps, cursor blink. Still under `prefers-reduced-motion`. No show character art is used.
- Phase 1 started. Rules (`mort/rules.py`) are plain functions that take observed values (alive, exit code, last log write, now), so tests use fake clocks and need no real jobs. Run tests with `python3 -m unittest`.
- Exit codes: `mort run` will wrap the command so the shell writes `$?` to a file when it ends, and mort records the wrapper's PID. A job that is gone with no exit file (killed, or adopted with `track pid`) counts as died.
- Stalled: alive and no log write for more than `stall_after` seconds. Exactly `stall_after` is not a stall. `None` turns the check off.
- Lock: the PID is read from one whitespace-separated field, set by index in config, so any one-line lock format works. An empty lock is free. A lock with no readable PID counts as stale, since it protects nothing.
- State: one SQLite table `jobs` in `~/.mort/state.db`. `last_event` holds the last event sent, so each event is sent once.
